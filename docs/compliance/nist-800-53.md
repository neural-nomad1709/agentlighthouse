# NIST SP 800-53 rev. 5 mapping (planning aid)

How AgentLighthouse mechanisms support 800-53 control implementation for an
agentic-AI workload. Scope: the controls the plane materially helps with —
not a full baseline; your system security plan owns the rest. Planning aid,
not an assessment.

## Access Control (AC)

| Control | Mechanism | Evidence |
|---------|-----------|----------|
| AC-3 Access Enforcement | Identity-bound tool policy: default-deny per SPIFFE identity; a tool runs only on an explicit allow whose argument constraints pass; explicit deny wins | `mcp_tool_call` receipts with `TOOL_NOT_ALLOWED` / `TOOL_DENIED` / `ARG_NOT_ALLOWED` |
| AC-4 Information Flow Enforcement | The egress choke-point: every network call mediated (fetch/CONNECT/reverse proxy); host+port allowlists; SSRF and DNS-rebind blocking that no allowlist overrides; outbound DLP on LLM prompts AND tool-call arguments | `fetch` / `http_forward` / `llm_call` receipts; block reasons `HOST_NOT_ALLOWED`, `SSRF_BLOCKED`, `SECRET_BLOCKED` |
| AC-6 Least Privilege | Per-agent identity with per-tool, per-argument allowlists ("least agency"); non-root containers, `cap_drop: ALL`, no-new-privileges; RBAC roles admin/operator/viewer in the governance layer | policy YAML under change control; `tests/test_hardening.py`; `/api/session` role surface |

## Identification and Authentication (IA)

| Control | Mechanism | Evidence |
|---------|-----------|----------|
| IA-2 / IA-9 User and Service Identification | SPIFFE-style agent registry (no identity -> deny at every ingress); per-user virtual keys and per-user governance tokens, hashed at rest, shown once | `NO_IDENTITY` / `INVALID_VIRTUAL_KEY` block receipts |
| IA-5 Authenticator Management | Ed25519 keys 0600-enforced (looser -> refuse start); provider keys only from env/secrets, `SecretStr`, never logged or receipted; revocation is immediate (`al vkey revoke`, `al-gov user revoke`) | `keys_test` suite; key files absent from image (tested) |

## Audit and Accountability (AU)

| Control | Mechanism | Evidence |
|---------|-----------|----------|
| AU-2 / AU-3 Event Logging and Content | Every mediated decision receipted: actor, action, target, verdict, block reason, findings (class+count, never plaintext), timestamps | the ledger itself; `spec/receipt-v1.md` |
| AU-6 Audit Review and Reporting | Evidence dashboard (search, trends, drill-down); SIEM export with MITRE ATT&CK technique ids and OWASP ASI tags | `al export`; dashboard e2e suite |
| AU-9 Protection of Audit Information | Append-only JSONL, SHA-256 hash-chained, Ed25519-signed; chain re-verified at every boot, tamper -> refuse to run; one writer per chain by topology | `al-verify` on any copy of the ledger |
| AU-10 Non-repudiation | Receipts signed with the mediator key; attestations and learned-rule bundles signed with the same key; independent verification requires only the public key | `al-verify` (standalone, MIT) |

## Configuration Management (CM)

| Control | Mechanism | Evidence |
|---------|-----------|----------|
| CM-3 / CM-5 Change Control and Access Restrictions | Config is an enforcement boundary: unknown keys refused, permissive settings gated to audit mode; every applied config lands as a **signed `config_change` receipt**; invalid reload keeps last-good; control plane unreachable from agents | `config_test` suite; `config_change` receipts |
| CM-7 Least Functionality | Default-deny everywhere (hosts, ports, tools); read-only root filesystems; agent network `internal: true` | compose topology tests; probe exit codes on every `up` |

## Incident Response (IR)

| Control | Mechanism | Evidence |
|---------|-----------|----------|
| IR-4 Incident Handling | Kill switch: four independent sources converge on one sentinel; deny-all at every ingress; engage receipted CRITICAL; `/healthz` stays answerable during the incident | `killswitch` receipts; SIEM alert |
| IR-5 / IR-6 Monitoring and Reporting | Blocks become SIEM alerts (`event.kind: alert`) carrying verifiable `record_hash`+`sig` | `al export --verdict block` |

## System and Communications Protection (SC)

| Control | Mechanism | Evidence |
|---------|-----------|----------|
| SC-7 Boundary Protection | Three-network topology: agents on an internal network whose only egress is the mediator; control plane on its own network; two one-shot probes prove both properties live on every `up`; L0 nftables ruleset for agent hosts | probe logs; `test_topology.py`; `al egress selftest` |
| SC-5 Denial-of-Service Protection | Per-domain rate + data budgets; per-user/org request + token budgets with atomic check-and-increment (race-proof on Postgres) | `RATE_LIMIT_EXCEEDED` / `BUDGET_EXCEEDED` receipts; 16-writer concurrency test |

## System and Information Integrity (SI) and Supply Chain (SR)

| Control | Mechanism | Evidence |
|---------|-----------|----------|
| SI-4 System Monitoring | L2 normalization + L3 scanning of inbound content, outbound prompts, tool responses, memory operations, and inter-agent messages | scan findings in receipts, MITRE/ASI-tagged |
| SI-7 Software, Firmware, and Information Integrity | Memory guard SHA-256 baselines (out-of-band tamper -> block + quarantine); skill guard pins instruction files; MCP descriptor pinning; learned rules load only from a signed bundle | `PROTECTED_KEY_TAMPERED`, `SKILL_DRIFT`, `TOOL_DESCRIPTOR_DRIFT` receipts |
| SR-3 / SR-4 Supply Chain Controls and Provenance | uv hash-pinned lockfile; SPDX SBOM per image (`make sbom`); cosign-signed images with the SBOM attached as a signed attestation (`make sign`); detect-secrets on our own repo | `dist/al-core.spdx.json`; cosign verification; `make lint` |

## Known limits (say them before the assessor finds them)

- The L3 scanners are dependency-free heuristics, not the named ML engines
  (the README's "What this does NOT do" section states the coverage limits).
- TLS CONNECT tunnels are policy-enforced by destination, not content
  (no MITM by design).
- nftables enforcement is rendered + tested but not yet validated on a
  production Linux host in this repo's CI.
